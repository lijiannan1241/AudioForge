Putting a 500-File Batch Into CI: A Reproducible Audio Delivery Pipeline

CLI, JSON presets and failure isolation mean no delivery depends on remembering what you clicked last time.

2026-11-17 · 722 words

中文版 → 中文

The most underestimated cost of batch audio is not the processing. It is knowing what settings were actually used. The result from the GUI is good, but next week a different person, a different machine, or a rollback to the previous VO set arrives — and nobody can reconstruct the effect chain order and thresholds. Reproducibility is not a luxury for large teams. It is what makes a delivery verifiable, repeatable and auditable.

Why "I can click it" is not enough

A GUI is for exploration: try a denoise amount, listen to the de-esser, settle on a loudness target. Once those decisions are made, they should be frozen into configuration, not left in someone's muscle memory.

The familiar sentence is: "I think it was -18 LUFS... or was it -19?" followed by half an hour of scrolling through chat history. If the parameters live in a JSON preset, that half hour disappears, and a new teammate can check out the repo and produce exactly your output.

What a complete command looks like

LoudPipe's CLI shares the same processing core as the GUI, so a CI run matches what you previewed locally:

loudpipe run \
  --input  ./vo_raw \
  --output ./vo_delivery \
  --preset ./presets/game_vo.json \
  --lufs -23 --true-peak -1 \
  --format wav --sample-rate 48000 --channels 1 \
  --report ./reports/vo_2026_11.json \
  -j 8 --retries 2

Several things matter here: the input directory is traversed as a whole, so 500 files do not need 500 lines; loudness target and true-peak ceiling are explicit rather than defaulted; the report lands as JSON for later steps to read and assert on; worker count and retries are tunable so a build machine does not saturate the CPU for other jobs.

Presets are configuration: write the effect chain as JSON

A preset stores order and parameters — denoise amount, de-ess frequency and depth, compressor threshold and ratio, three EQ bands, normalization target. Order is part of the configuration: denoise-then-compress and compress-then-denoise produce different files.

Committing the preset to your repo adds version control to audio delivery. A change is one diff that can be reviewed and reverted. This matters in game projects, where art and audio assets for multiple versions coexist and an older VO pack may need to be delivered again.

Failure isolation and resume

The worst thing in batch work is dying at 97% and starting over. LoudPipe treats each file as an independent task: a decode failure does not abort the batch, failed items are recorded separately, and a rerun only touches those files. Finished outputs stay untouched.

Use this deliberately in CI: have the build script read the report and fail the pipeline on any nonzero failure count, then rerun in resume mode after fixing. Do not treat "mostly succeeded" as success — one silent file in a delivery is harder to catch than a total failure.

The report is the acceptance sheet

Every batch writes CSV / JSON / HTML reports with per-file input and output LUFS, true peak, clipped samples, DC offset, duration and format, plus waveform and STFT spectrum images.

They are not only for humans. CI can read the JSON and assert hard checks: output LUFS within ±0.5 of target, true peak at or below -1 dBTP, clipped samples all zero. Turning "sounds fine" into a few checks that fail is the step that brings audio into an automated workflow.

Handing off to Wwise / FMOD

The engine does not want the "best sounding" file. It wants a consistent one: unified sample rate, bit depth and channel count; naming and folder layout that match project conventions; metadata preserved. LoudPipe aligns those at export, and the resulting WAV / MP3 / FLAC / M4A goes straight into the engine import pipeline. Chapter markers, essential for audiobooks, can also label multiple variants inside one delivery.

Wrap-up

A reproducible pipeline does not need more tools. It needs the decisions you already got right, written down: presets in version control, parameters in the command line, acceptance in the report. Next delivery, you are not recalling what you clicked — you are running the same command again.
